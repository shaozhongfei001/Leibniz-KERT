## 7. 操作风险（踩过的坑）

### 7.1 ⚠ 有另一个会话与你在**同一个 git 工作目录**里工作

实测后果（2026-09-14 真实发生）：

1. 对方把 HEAD 切到 `recover/PI-ARCH-product-catalog` → 我 `git commit` 的提交落在**那条分支**上；
2. `git push origin feature/GK-KE-L0-contract` 推的是**分支引用**（`ca47192`），报
   `Everything up-to-date` —— **我的修复实际从未上远端**，而那轮 CI 自然不含我的修复；
3. 同期还出现：我没改过的 5 个 `generated/**`、`specs/semantic/**` 改动；`secret-scan` advisory 计数 +1。

**规避**：不要让两个会话共用同一工作目录；或各自用 `git worktree`。
**补救手法（已验证可用）**：

```bash
git worktree add -q /tmp/gk-fix <目标 sha>      # 隔离检出，不动他人工作目录
cd /tmp/gk-fix && git cherry-pick <你的提交...>
git push origin HEAD:refs/heads/<目标分支>
cd <原仓库> && git worktree remove --force /tmp/gk-fix
```

### 7.2 提交/推送前**必须**核对「我到底推了什么」

`git push` 成功 ≠ 你的提交上去了。**推完必须核对**：

```bash
git rev-parse --short HEAD
gh api repos/<owner>/<repo>/git/ref/heads/<branch> --jq '.object.sha[0:7]'
git branch -r --contains <你的 sha>        # 空 = 没上去
```
