## E. 流程规则（本轮确立，跨轮适用）

| # | 规则 | 触发原因（实证） |
|---|---|---|
| **E-1** | **变异自证的恢复校验必须三重比对**：① 期望/HEAD sha ② **变异前记录的 `wc -l`** ③ **变异前记录的净增量（`git diff --numstat`）**；三者都回原值才算恢复成功 | 本轮实证：本批 M-A1 变异**恢复**时 `old_str` 覆盖不足，把"修正记录"段落**插回两遍**（`specs` 238-241 与 243-246 逐字节重复，`f7749af` 为 0 次）⇒ **sha 比对没抓到，因为参照物（HEAD）本身已被污染 —— 它可以"一致地错"** |
| **E-2** | 引用实现代码一律 **"函数名 + 行号"双锚**；**并发编辑期的跑数不可归因**（先冻结再跑）；引用需记**行号基准快照** | 见 D-8/A-8：`server.py` 本批净 **+28** 行致旧引用大面积漂移；且**同一批快照内漂移并不一致**（一份 +28、一份正确） |
| **E-3** | **定稿必须落决策清单** —— commit message 不作为可核对记录 | 见 §C-4 节首教训 |
| **E-4** | 提交前若涉及**大段文本**，须先看一次 **diff 摘要**（不止核指纹/版本/断言） | 本轮 TL 自认：核了指纹/版本/用例却漏掉"重复段落"，缺陷被提交进 `e3bcefe` |
| **E-5** | **sha 引用口径**：凡报告 sha 一律取**入库 HEAD 版本**（`git show HEAD:<path> | sha256sum`）；引用"工作区值"须**显式标注**；两者不一致时**必须同时给出并说明差异** | 本轮实证：m71 报的 schema `5abfa6de…` 在其补 `assetVersion` 澄清后**即作废**（入库值 `d8f9b6b6…`）；而 TL 最初复核时**拿工作区值去比其 HEAD 值** ⇒ 误判其"报数不符"。立此规则**双向消除歧义**（既约束报告方，也约束复核方） |
| **E-6** | **文档类交付协议（提交时机）**：对**正在被编辑**的文档类交付，**由交付方先"声明定稿"（给出 sha + 行数），TL 再提交**；TL **不提交中间态** | 本轮实证：同一份文档在 TL 两次提交之间走了 **849 → 861 → 865**，TL 追了**三次**中间态，并因此在提交信息里写出**陈旧行数**（`f616325` 信息中"861 行"，实际入库 **865 行 / `1cdc1c4c…`**）。⇒ 不是纪律问题，是**协议缺失**；E-5 管"sha 怎么引用"，E-6 管"何时提交" |
