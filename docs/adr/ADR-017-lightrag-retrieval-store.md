# ADR-017：接入 LightRAG 检索（外部只读；索引在 KERT 工作区之外）

> 状态：CANDIDATE_AWAITING_OWNER
> 日期：2026-09-16
> 依据：Owner 2026-09-16 明示"要 lightRAG"（**D-31**，推翻 D2-A/D3-A）；原 **D2-C** 明载"引入 LightRAG 并落盘｜**需规格修订 + 新 ADR + Owner 决策**"
> 替代/变更：对 KERT-SPEC-001「**不得把其数据库文件作为持久化事实源**」（§6.3）与「**无数据库依赖或隐藏持久化数据库文件**」（§18.5）的**受控变更记录** —— 本 ADR 论证该二条**未被触发（满足原意）**，**不是**请求豁免（见「论证」）
> 实现：`src/kert/infrastructure/lightrag_client.py` + `KnowledgeService.retrieve_via_lightrag`（检索）／`KnowledgeService.publish_artifact`·`retract_artifact`（**数据出口**，见「数据出口」一节）

## 背景

既有检索面（Kùzu + Parquet + 确定性打分）不承担 GraphRAG 类检索；Owner 要求引入 LightRAG 或同类框架。
本机已有可用实例（`/home/szf/dev/lightrag`，端口 9621，程序化调用经 `X-API-Key`，embedding 走 Ollama `11434`）。

⚠ **语料归属（2026-09-16 更正；Owner 澄清）**：该库内容是**本地测试文档**，与 KERT／`gits-*` **不同源**，
且**可全部清空** ⇒ 早先写的"语料为其自身的银行制度/产品文档（只读、不写回）"**已过时**：
本库现已**清空并由 KERT 产物重建**（见「前提更正」「⑧ 清空-重建」）。

**库规模**（判据＝ `rag_storage/graph_chunk_entity_relation.graphml` 的 `<node>`/`<edge>` 计数）：

- **历史基线（清空前，2026-09-16 实测）**：**662 节点 / 784 边**（712 KB）—— 清空后**不再适用**；
  ⚠「≈8.7MB（≈7851 实体）」取自 `rag_storage.bak-20260909/`（旧备份：7851 节点 / 9013 边 / 8.45 MB）
  与 `start.sh` 旧注释（该脚本提示里"90MB / 7851 实体 / 3-5 分钟"同为陈旧文本）⇒ **不沿用脚本注释**；
- **现基线（清空 → 只灌 KERT 最小集后）**：**5 篇文档 / 78 节点 / 86 边**（见「① 可重建性」）。

## 决策

KERT 以「**只读接入外部 LightRAG server**」的方式使用 LightRAG：连接参数走 env
（`KERT_LIGHTRAG_URL`/`KERT_LIGHTRAG_API_KEY`/`KERT_LIGHTRAG_TIMEOUT`），经 `POST /query/data` 取
**实体 + 关系 + 出处**；**不内嵌** `lightrag-hku`、**不在 KERT 工作区落索引**。

## 边界

- 索引位于 KERT 工作区**之外**（`/home/szf/dev/lightrag/rag_storage`）⇒ **工作区内不新增任何持久化索引文件**（§18.5 的工作区口径不变）；
- **不是事实源**：KERT **只读**消费；**不写回** `01_raw`/`02_work`/`03_core`/`04_serve`；知识权威源仍是文件树（"文件目录为权威源"原则**未改变**）；
- **检索失败不静默**：不可达/超时 ⇒ `LIGHTRAG_UNAVAILABLE`；非 2xx（含 401/403/404）⇒ `LIGHTRAG_HTTP_ERROR`；形状不符 ⇒ `LIGHTRAG_RESPONSE_INVALID` ⇒ **禁止返回空结果**。

## 论证：为什么这是「满足 §6.3 原意」而不是「推翻 §6.3」

§6.3 原话约束的是「**把（引擎自身的）数据库文件作为持久化事实源**」。本方案下：

1. **索引不是 KERT 的事实源** —— 检索侧只读、不写回工作区；**整体丢弃它不影响任何 KERT 产物**
   （`03_core`/`04_serve` 一字不变）；且它**可由 KERT 产物重建**（2026-09-16 起：清空 ⇒ 重灌 KERT 最小集
   ⇒ 检索**覆盖与出处一致**，见「① 可重建性」）⇒ 它是**派生物**，**不是**权威源；
2. **索引不在工作区内** —— `01_raw..04_serve` 无新增的强制持久化文件；
3. 故该条**未被触发**（不是被豁免），§18.5 的"无隐藏持久化数据库文件"在工作区口径内**仍成立**。

## 可验证判据（本形态下可机械核对）

1. **不写回工作区**（"不是事实源"的机械证据）：调用 `retrieve_via_lightrag` 前后**工作区文件集合与内容零变化** —— 已落测试；
2. **不静默失败**：不可达 / 鉴权失败 / 形状不符 ⇒ **具名**错误（三类码）—— 已落测试（含"可达但 404/405 必须红"）；
3. **KERT 自有产物可重建**：`03_core` → `04_serve` 由既有 pipeline 重建（既有能力与既有判据）。
4. **删索引 ⇒ 重建 ⇒ 检索覆盖与出处一致**（2026-09-16 实测；判据分两层，**只主张第一层**）：
   - **确定性成立（判据）**：清空后用**同一 KERT 文档集**重建 ⇒ 文档集合与各 query 的**引用出处**
     （`file_path`）**完全相同** —— 实测 6 个 query×mode 组合的出处集合 Jaccard = **1.00**，
     且两轮的**出处全集亦相同**（5 条 `03_core__…`／`04_serve__…` 标识）；
   - **非确定性（如实记录，不假装确定）**：实体/关系抽取经 LLM（Ollama）⇒ **图规模与实体集不稳定**：
     两轮重建分别为 **88/86 与 78/86** 节点/边；`mix` 模式实体集 J = **0.36 / 0.13 / 0.23**、
     关系数 40/53、34/69、59/52（**逐轮不同**）；`naive`（纯向量）模式实体集**完全一致**（J = 1.00）。
   ⇒ 判据**不**主张"逐字/逐实体一致"；**覆盖与出处一致**才是可主张、且已实测的部分。

## 数据出口（P-1：把 KERT 产物**发布**到外部实例）

发布是**写**动作，与只读检索性质不同，故单列一节（发布什么 / 发布到哪 / 如何撤回）。

**① 发布什么（白名单）**：仅 `03_core/**`（知识资产）与 `04_serve/**`（发布投影、本体物化产物）
—— 即 `KnowledgeService.EGRESS_ROOTS`；`01_raw/**`、`02_work/**`、`90_control/**`（可能含草案与凭据）
**一律拒绝**（具名 `LIGHTRAG_ARTIFACT_REFUSED`）。

**② 发布到哪**：`KERT_LIGHTRAG_URL` 指向的实例（缺省 `http://127.0.0.1:9621`）的 `rag_storage/`
—— 仍在 KERT 工作区**之外**；接口 `POST /documents/text`，凭据走 `KERT_LIGHTRAG_API_KEY`。

**③ 出处（可回译，机械可核）**：`file_source = artifact_file_source(rel)`
（`04_serve/<svc>/version=<v>/ONTOLOGY.md` ⇒ `04_serve__<svc>__version=<v>__ONTOLOGY.md`），
正文再前置**出处头**（相对路径 + sha256）。⚠ **实测**：lightRAG 对 `file_source` 做 **basename**
规范化（目录被吃掉）⇒ 直接送相对路径时检索命中的 `file_path` 只剩 `ONTOLOGY.md`、**出处丢失**；
`/`⇒`__` 后实测命中形如 `03_core__customer__version=2026.09.07.1__entities__CUST-CORP-0001.md` ⇒
**回指 KERT 产物路径 + 版本**（`parse_artifact_file_source` 可逆，测试断言往返）。

**④ 幂等**：**先查后写**（同 `file_source` 已存在 ⇒ `already_published`，不发写请求）。
⚠ **实测**：服务端的 409 去重发生在 doc_status **落库之后**，而索引是**异步**的 ⇒ 紧跟其后的重复插入
**可能不被拒**（会生成 `dup-*` 失败条目）；且 `POST` 返回 200 后条目要过一会儿才可见
⇒ 发布后须**等可见**（`wait_until_present`）再返回，撤回亦须留可见性窗口。

**⑤ 如何撤回**：`KnowledgeService.retract_artifact(rel)` ⇒ 按出处标识找出**全部**条目（含 `dup-*`）
⇒ `DELETE /documents/delete_document` ⇒ 等全部消失（异步）。**实测**：灌入 3 件（本体物化产物
`ONTOLOGY.md` + 2 件工作区资产）⇒ 图规模 **662 节点/784 边 → 734/861（+72/+77）**；
撤回 3 件 ⇒ **回到 662/784**（**完全可逆**）。

**⑥ 只读工作区**：发布与撤回**都不写工作区**（测试机械断言：前后文件集合与内容逐字节一致）。

**⑦ 跑该测试的前置与收尾（口径，防后人留残留）**：`tests/integration/test_lightrag_publication.py`
对**外部实例有写操作**（灌入 + 撤回）⇒ 前置＝实例**可写**（`KERT_LIGHTRAG_API_KEY` 具写权限）；
**结束必须回到测试前的实例状态**：测试在 `finally` 中 `retract_artifact`，并以**稳定性**断言收尾 ——
**连续 2 次**读都为空才放行（删除**异步且分阶段**：先状态、后 chunks/向量/图；单次读可能仍见残留）。
（实测：测试前后均为 **5 篇文档 / 78 节点 / 86 边**）。⚠ "回基线"＝**回测试前状态**，
**不是**历史值 662/784（该值随语料变更而变；见「背景」的历史/现基线）。
⚠ **测试必须自持唯一出处标识**（`P1-PROBE-<uuid8>.md`）：曾用真实产物名 ⇒ 与真实文档**撞名**
⇒ 幂等判定"命中已有"（断言红）且 `finally` 的撤回**误删真实文档**（实例 78/86 → 61/62，实测）。
若中途异常退出，按 ⑤ 手动 `retract_artifact` 回滚。

⚠ **两个可见窗口须分清（2026-09-16 实测，防误判为"残留"）**：

- **(i) 测试运行中**：探针自发布至撤回之间**确实存在**（此时读库会看到 **6 篇**，含 `P1-PROBE-*.md`）
  —— 这是**设计使然**（TL 曾于测试期间读到，属此类）；
- **(ii) 测试返回后**：实测（退出后每 2s 轮询 **0–42s**）**无探针条目**、条目数恒为 **5**
  ⇒ 任何"库是否干净"的判定都应放在测试**退出之后**，且以"连续多次为空"为准；**不要在测试运行中读库**。

**⑧ 清空-重建（操作顺序与回退凭证）**：

1. **备份**：`stop.sh` ⇒ `cp -a rag_storage rag_storage.bak-TL-20260916` ⇒ 保真核对
   `diff -r rag_storage rag_storage.bak-TL-20260916`（**空＝逐字节相同**；本次实测 IDENTICAL）；
   回退凭证：文档条目 **7**、graphml **662/784**、体积 **9.0M**（旧备份 `rag_storage.bak-20260909/` **勿动**）；
2. **清空**：停服 ⇒ `rm -rf rag_storage/*`（**保留目录本身**）⇒ `start.sh` ⇒ 确认**空库**
   （文档数 **0**、graphml 尚不存在即 **0/0**、`status_counts` 全 0）；
3. **重建**：经「数据出口」发布 KERT 产物（本轮最小集 **5 篇**：本体物化 `ONTOLOGY.md`
   + 3 件 `03_core` 实体 + 1 件 `04_serve` 投影说明）⇒ 逐篇等 `processed` ⇒ 记 **5 篇 / 78 节点 / 86 边**；
4. **回退**：`stop.sh` ⇒ `rm -rf rag_storage/*` ⇒ `cp -a rag_storage.bak-TL-20260916/. rag_storage/` ⇒ `start.sh`。

## 回滚与重建

- **回滚**：移除 `retrieve_via_lightrag` 与其测试（或使 env 指向空/不可达）⇒ 系统回到"无检索增强"；
  **工作区不受影响**（实现**零写入**工作区）。
- **重建**：索引**可由 KERT 产物重建**（操作与回退见「⑧ 清空-重建」；判据见「可验证判据」4 ——
  只主张"**覆盖与出处一致**"，**不**主张逐字/逐实体一致）；KERT 侧重建仍指 `03_core`→`04_serve`。
- 若改为形态 (ii)：**必须**随该变更给出"索引落在**工作区内**"的规格字句，以及对应的重建/一致性判据
  （判据可复用「可验证判据」4，但"**工作区内落盘**"这一点须另行显式处理）。
