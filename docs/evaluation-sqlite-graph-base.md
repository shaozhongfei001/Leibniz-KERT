# 评估：DKWS 平台内以 SQLite 作为小型知识图谱数据库底座的合理性

> 评估人：DKWS 技术经理/架构师
> 日期：2026-08-21
> 依据：DKWS-SPEC-001 V1.0（状态 DRAFT_CANDIDATE）当前文本 + 已实现工程（`dkws/`）
> 结论先行：**技术上合理，但与规格硬约束冲突，默认不可引入；如确有需要，必须走受控变更（Owner 决策 + 规格修订 + ADR 记录），或仅以"内存 SQLite 查询加速层（不落盘、可重建）"形态出现并明确声明。**

---

## 1. 需求背景（为什么考虑 SQLite）

DKWS 已实现文件化知识图谱（§15.4）：节点来自 `entities.parquet`、边来自 `relations.parquet`，服务启动时构建内存邻接表（`application/services.py` 的 `graph()`）。当前能力边界：

| 场景 | 现状（内存邻接表） | 业务方潜在诉求 |
|---|---|---|
| 一跳邻居 | ✅ 支持 | — |
| 有限深度路径（depth≤3） | ✅ BFS 支持 | 更深/不定深路径、传递闭包 |
| 图谱过滤（时间/类型组合） | ⚠️ 需全量遍历 | 索引化过滤 |
| 关系型联合查询（图谱+声明+数据集） | ❌ 需多表拼装 | 一次查询返回复合结果 |
| 事务/并发写 | ❌ 只读投影 | 评审/发布期间的临时写 |

SQLite 在这些场景技术上成立：节点/边表 + B+Tree 索引 + `WITH RECURSIVE` 递归查询 + 单文件零运维。

## 2. SQLite 方案的技术合理性（独立于规格）

| 维度 | 评估 |
|---|---|
| 功能匹配 | ✅ 节点/边/属性表、二级索引、递归 CTE（深度/闭包）、JSON 函数——足够支撑"小型知识图谱"（万级节点/十万级边，规格 NFR-006 量级） |
| 性能 | ✅ 本地单文件、内存缓存页；10 万边深度查询 P95 远优于逐文件扫描（NFR-005 基线内） |
| 部署/运维 | ✅ 零服务、单文件、备份即复制；符合"不依赖基础设施"精神 |
| 一致性 | ✅ ACID 事务，优于文件原子写的弱一致性 |
| 规模上限 | ⚠️ 单写者模型下没问题；多写者需外部锁协调（规格默认单写者 ADR-008） |
| 技术栈 | ✅ Python 内置 `sqlite3`，无新增依赖 |

**技术结论：SQLite 作为图谱查询/存储引擎本身完全合理，是业界成熟的嵌入式方案。**

## 3. 与 DKWS 规格的硬约束冲突（逐条）

| 规格条款 | 原文（要点） | 冲突 |
|---|---|---|
| **§1.5 明确排除** | "本期不实现：MySQL、PostgreSQL、**SQLite**、Neo4j、Elasticsearch、Milvus 等任何持久化数据库" | **直接冲突**：SQLite 在排除列表 |
| **§2.2 不变量 6** | "图谱只是权威对象、关系和声明的一种投影，不是唯一事实源" | 冲突：SQLite 若成为事实源，违反"投影"定位 |
| **§6.3 技术约束** | "允许使用内存计算引擎读取 Parquet，但**不得把其数据库文件作为持久化事实源**" | 落盘 SQLite 文件 = 持久化事实源，违反 |
| **§15.4 文件化图谱** | "服务启动时可构建内存邻接表，但**不得写成数据库事实源**" | 冲突：图谱必须保持"从 Parquet 可重建" |
| **ADR-002** | "不使用持久化数据库：满足模拟、可复制和文件透明性目标" | 冲突：引入即推翻 ADR-002 |
| **§18.5 验收标准** | "**无数据库依赖或隐藏持久化数据库文件**" | 冲突：验收将不通过 |
| **§20.1 强制实施规则 3** | "不得引入数据库、消息队列或分布式基础设施" | 冲突：Agent 实施强制规则 |

**结论：规格文本层面，落盘 SQLite 图谱库被明确禁止，引入将导致：验收失败（§18.5）、ADR-002 被推翻、规格"文件透明/可复制"目标受损。**

## 4. 引入 SQLite 的后果与责任

1. **规格状态**：DKWS-SPEC-001 为 `DRAFT_CANDIDATE`，但"不引入数据库"是 §20.1 对实施 Agent 的强制规则——静默引入 = 违反实施纪律（§20.1 第 3 条）。
2. **可复现性**：§18.4 可重建性测试要求"删除 Work/Serve 后仅凭 Core 重建"——SQLite 若存了图谱查询状态，重建比对将断链。
3. **证据链**：图谱查询结果必须回传权威 ID 与证据（§2.2 不变量 7、§15.5）——SQLite 只是新一层投影，若未同步维护证据字段会破坏溯源。
4. **验收**：§18.5 "无数据库依赖或隐藏持久化数据库文件" 直接判定不通过。

## 5. 建议与替代方案

### 方案 A（推荐，严格遵循规格）：保持文件化图谱，强化现状

- 维持 `entities.parquet`/`relations.parquet` + 内存邻接表；
- 需要更深的递归/闭包时，在**内存中**实现迭代式传递闭包（DFS/BFS 升级），不落盘；
- 需要复合查询时，用 PyArrow 的**内存表 join**（DKWS 已依赖 PyArrow，§6.3 允许内存计算引擎）；
- 优点：零规格冲突、可重建性/审计/验收全部保住；缺点：无持久化索引，超大图（>NFR-006）性能受限于内存。

### 方案 B（受控变更，若业务确需 SQLite）：走正式决策流程

若业务方明确需要 SQLite 级查询能力，**不能静默引入**，需：
1. Owner 正式决策（记录于 `90_control/decisions/` 与规格变更记录）；
2. 修订规格：§1.5 移除 SQLite 排除项或改为"允许受控查询加速库"；ADR-002 追加修订（如 `IMP-ADR-011`：SQLite 仅作**投影查询加速层**，非权威源）；
3. 明确 SQLite 定位与边界：
   - 数据来源唯一为 `03_core` 投影构建（`build-projection` 时从 Parquet 重建，纳入 §18.4 可重建性测试）；
   - SQLite 文件置于 `04_serve/.../graph.db`（可重建层），**禁止进入 `03_core`**；
   - 图谱查询结果仍回传权威 ID + 证据引用；
   - 验收标准 §18.5 相应更新（"无隐藏持久化数据库文件"→"图谱库可从 Parquet 重建且非权威源"）。
4. 若走此路，我可以在 DKWS 工程内实现 `graph_cache` 模块（SQLite 构建器 + 重建脚本 + 可重建性测试）。

### 方案 C（灰色地带，需明确声明）：内存 SQLite 查询加速

- `sqlite3` 以 **`:memory:`**（或显式临时文件 + 启动即删）加载 Parquet 图谱，仅作本次进程的查询加速，**不持久化**、进程退出即消失；
- 规格 §6.3 "允许使用内存计算引擎读取 Parquet" 的精神可覆盖（无持久化文件、可从 Parquet 重建）；
- 风险：容易滑向落盘（`:memory:` 一旦误用 `connect("file.db")` 即违反）；**必须**配套测试断言无 `.db` 持久文件、文档声明为进程内加速层。
- 若选此方案，我实现时保证：库文件不存在于工作区、重建自投影、验收仍满足"无隐藏持久化数据库文件"。

## 6. 结论

| 项 | 判定 |
|---|---|
| SQLite 技术合理性 | ✅ 合理（嵌入式、递归查询、零运维） |
| 与规格冲突 | ❌ **默认不可引入**（§1.5/§2.2/§6.3/§15.4/ADR-002/§18.5/§20.1 多条硬约束） |
| 推荐路径 | **方案 A**：维持文件化图谱 + 内存增强（零冲突、保验收） |
| 若业务强制需要 | **方案 B**：Owner 受控变更（规格修订 + ADR-011 + 定位为投影查询加速层 + 可重建性测试） |
| 灰色折中 | **方案 C**：内存 SQLite（:memory:）查询加速，须严格不落盘并测试断言 |

> 作为技术经理/架构师，我建议**默认采用方案 A**；若业务方以查询性能为由坚持 SQLite，请给出量化的性能差距（基线：NFR-005 一跳 P95≤1s 已在内存邻接下达成），再决定是否启动方案 B 的受控变更。
